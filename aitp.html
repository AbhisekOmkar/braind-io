Problem 01

VPN routing and Intact iQ querying took longer than expected

What happened

Getting from Braind's cloud into the client's network meant VPN routing, and querying the ERP directly was slow to set up.

What I would do

  • Do not route input a small connector beside Intact iQ, inside the client network, that only dials out. Cloudflare Tunnel or Tailscale. No inbound port, so no firewall project.
  • A read API, not a databasethe connector exposes customers, orders, invoices and categories as a small versioned API. The cloud never sees the ERP itself.
  • Copy, then querya nightly extract into our own Postgres. Cross-sell analysis runs on the copy, so a slow ERP query is never on the critical path.
  • Use what the ERP offersIntact iQ has its own REST API definitions in Setup. Define the four or five reads there and the definitions become the contract.
  • Heartbeatthe connector reports its last successful sync. A dead link is a red tile on the dashboard the same hour.

Where I have done it

Sidecar runs exactly this shape: one connector per system (an ERP connector for Odoo, a database proxy for Postgres), services talking on a private network with health checks and an explicit start-up order, secrets pulled from a cloud secret manager, and nothing exposed to the outside. Trace's records are copies in our database; the client's systems are only read through connectors.

Problem 02

The exact Intact endpoints for order history and closed-won data were unclear

What happened

Nobody could say which endpoint or table held order history and closed-won deals, so the build guessed and re-guessed.

What I would do

  • Write the contract firstfor each question the client wants answered (top customers, category history, lapsed purchases, closed-won), name the source, the field, the grain and one real example record the client vouches for.
  • Prove it with 20 recordspick twenty orders the client knows by heart, pull them through the contract, and score every field: matched, mismatched, missing. Fix until the score is clean.
  • Keep it in the repothe contract is versioned config per client, not knowledge in one head. When the ERP changes, the check fails first.
  • Match in tiersexact ID, then a stable key like customer number or email domain, then a fuzzy step with a human queue. Record which tier matched each row.

Where I have done it

Trace's ERP verification does this every day: each shipment record is checked against the client's ERP leads in tiers (lead number, then customer plus port, then none), with fast deterministic matching first, a small model only for the last mile, and the matched and mismatched fields stored per record with what it cost. The per-client config file (domains, mailboxes, tracking-number patterns) is the same idea as a data contract, and the customer-service assignment on every record carries the method that matched it.

Problem 03

Outlook and Graph permissions had to come from the client

What happened

The build waited on the client's IT for Microsoft Graph permissions, and the wait was invisible in the plan.

What I would do

  • Make the ask a productone verified multi-tenant app and one admin-consent link. The admin clicks, signs in, and lands on a page where they tick the mailboxes in scope.
  • Permission per mailboxeach tick becomes one Exchange role assignment scoped to that mailbox. The app holds no tenant-wide mail permission at all.
  • Drafts, not sendsthe engine writes into the rep's Drafts folder. No send permission is ever requested, so the consent screen is short and the rep stays in control.
  • A fallback that needs no adminif the client will not grant an app anything, per-user consent through Nylas works the same week, one link per person.
  • Put the dependency on the planconsent is a named task with an owner and a date, and the build has a stub to run against until it lands.

Where I have done it

Sidecar started on Nylas, with per-user consent links, webhooks and a router that forwards each mailbox to the right agent. Then we built email-harvester in-house: Graph app-only auth, zero mail permissions on the app registration, one role assignment per mailbox, an admin consent link and a chooser page, notifications plus delta sync plus a two-hourly reconcile, and a drift detector that catches the one setting that silently widens access. It runs 70-plus mailboxes across nine customers.

Problem 04

Recent data was still being migrated, so newer figures looked incomplete

What happened

The numbers for recent months looked low because the data behind them had not all arrived yet.

What I would do

  • Watermark every dataseteach source carries "complete up to" a date, and every number is published with it. Queries stop at the watermark.
  • Count against the sourcerows per month here against rows per month there. A short month turns red before anyone reads a chart.
  • Trend beside the averagenever show a cumulative average alone. The monthly line goes next to it, so a fall cannot hide.

Where I have done it

Trace's records carry a watermark of how many messages are folded in, evaluation replays use a time cutoff so the system cannot see the future, and a completeness check is what found 21% of customer requests were never being traced. Braind's own CWSI note, where a cumulative average hid a falling lead count, is the same lesson.

Problem 05

Inconsistent company names created duplicates and matching problems

What happened

The same customer appeared under several spellings, so matching produced duplicates and missed links.

What I would do

  • Stable keys firstcustomer number, email domain, company registration or VAT number. Names come last.
  • Then normalisestrip Ltd, Limited, PLC and friends, expand abbreviations, drop punctuation, keep an alias table so each decision is made once.
  • Then a queue, not a guessthe fuzzy leftovers go to a person with both records side by side. Never merge two companies on a name alone.
  • Report itduplicate rate is a number on the dashboard, with the worst offenders listed.

Where I have done it

Trace's customer matching uses the email domain as the primary key, a name normaliser for the rest, and a matcher for ERP organisations that tries deterministic layers before a small model. The hard lesson was a merge on a weak identifier that put two customers on one shipment record; the fix was to refuse when the evidence is ambiguous, because a refusal is cheaper than a wrong merge.

Problem 06

Some signals needed de-duplication and stronger geographic gating

What happened

External signals such as website visits, funding news and "same building" arrived noisy and repeated, so the queue filled with the same thing.

What I would do

  • Fingerprint every signalcompany, type, source and time bucket. A repeat is dropped, not shown twice.
  • Hard gatesa distance rule for nearby signals and a confidence score for the rest. One signal per company per day.
  • Test before you switch onlabel a hundred signals by hand, measure precision per source, and every source has a kill switch.

Where I have done it

Trace de-duplicates three ways (message ID, the RFC message ID across mailboxes, and a content fingerprint), and the nightly memory sweep uses fingerprints and a significance score so only meaningful changes cost a model call. Braind's Tecknuovo note, where real data produced a mountain of duplicate signals, is the same problem.

Problem 07

Industry and margin questions could not be answered because cost data was not available

What happened

The "Ask the OS" layer was asked about margins, but the cost data behind margins had not arrived.

What I would do

  • Say what you do not knowevery answer carries its source, and "not available" is a real value the user sees, not a guess.
  • Stage the questionsrevenue-only answers now, margin answers on the day cost data lands, with that date shown.
  • Refuse with a reasonan assistant that cannot answer should say which data is missing and who owns it.

Where I have done it

Trace's extraction records where each fact came from (the email body, a registry, memory), and the worst incident in that system was a remembered value filling a field the customer never stated. The fix was to make a gap a gap: a missing field stays missing and gets asked, never filled from a guess.

Problem 08

The engine found 418 opportunities and 49 were acted on

What happened

The system produced insight, and 354 opportunities sat untouched. Insight did not become behaviour.

What I would do

  • Make activation the metricacted-on rate sits on the dashboard next to opportunities found, from day one.
  • Owner and due dateevery opportunity has a rep and a date, and the untouched ones go to the sales lead weekly, by name.
  • Meet the rep where they worka ready draft in their Outlook Drafts and a nudge in Teams. The dashboard is the record, not the workplace.
  • Log every actionsent, edited, dismissed, and the edits themselves. That stream re-ranks next week's queue and is the roadmap.

Where I have done it

Nothing in Sidecar sends itself: every output is a draft card a person approves or edits, and every edit is logged and used as the test set. The rule that came out of a silent failure, alert on absence and not only on errors, applies here too: an opportunity nobody touched for a week is a signal, not a row. Braind's Tecknuovo users asked for the same thing when they wanted the intelligence inside Slack.

Problem 09

A Unicode error kept the live workflow broken for about ten days

What happened

The email generation step failed repeatedly on a bad character, while the project was still described as delivered.

What I would do

  • Alert on silencea check that counts outputs per day and pages someone when the count is zero. Errors are loud; absence is what kills.
  • Clean at the boundarystrip control characters and bad encodings before anything is saved or sent. Cheap, and it never happens twice.
  • One definition of done"delivered" means the client can see the result in their own system, not that our dashboard is green.
  • Errors get an ownerevery failure lands in a ticket with a name on it, and the weekly review starts from the open ones.

Where I have done it

Trace saw six saves fail on a stray NUL byte and now strips them before every write. Cost and volume are instrumented like correctness, because the worst failures throw no error: that is how a runaway loop and 21% of silently dropped replies were caught. Sidecar's engine turns logs, traces and error reports into ranked incidents with a draft fix attached, so a ten-day-old failure cannot sit unowned.

What I would build first

Five things, reused on every client

  • The connector kittunnel, read API, nightly copy, heartbeat. Reused on every client with an on-premise system.
  • The data contractper client, in the repo, proved against twenty real records before the first feature.
  • The permission productone consent link, per-mailbox scope, drafts not sends. Consent becomes a dated task, not a wait.
  • The activation loopowner, due date, draft where the rep works, every action logged, untouched work escalated.
  • One definition of donethe client's own system is the scoreboard, and silence pages someone.
