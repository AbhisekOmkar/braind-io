What you've actually built

Q01

The biggest thing you've built with AI

Sidecar was working on a feature called Trace which was generating Million Dollar for the company. The problem was freight forwarder pricing desk runs on email one shipment = dozens of emails across several mailboxes, threads, people. Subjects mutate, threads get reused, identifiers arrive late or never. Nobody has the whole story of a shipment in one place. Handlers dig the email agent has no memory of what already happened on that deal. Trace is one typed narrative pre shipment rebuilt from that mess. Two consumers the email agent (as its memory of the shipment) and the eval system as ground truth for grading the agent.

Every inbound and outbound email via nylas webhook across all mailboxes at a tenant level with attachments as well PDF, CSV etc.

First resolve which emails belong together, reply chains, shipment ids subject rules, fetch metadata batch wise, pre classify 60% of message by rule, build complete evidence board. Then a bounded model call judges the board what belongs to what the shipment state is Prompt forbids discovery it can only judge what's on the board hard budgets on toll calls and token enforcement in code by scaffolding in agent harness in using open ai agent sdk. Then format the typed record save via strict typed check run ends when save commit.

One record per shipment timeline, parties, cargo, ports, status, with every claim citing the email it came from Under 150 words of narrative memory the agent reads before it acts 25k generation runs a week at 98.4% success 27.5k+ live shipment records new records created on the live path with zero LLM calls. Incremental update median 8.4 s, 94% of that is the model.96% of attachable mail attached within five minutes $0.11 per record.

Q02

How do you know it's right?

(a) Validation before deployment works from first principles, do not ask if the model is good, ask what exactly must be true before this touches a customer, then turn each of those into a measurable gate. In production that looked like this before any change shipped, we replayed real historical emails through the unmodified pipeline with temporal cutoffs so the system could not see the future, graded results deterministically wherever possible with LLM judges only for gray zones, and enforced hard per tenant thresholds in CI (should reply F1 at least 0.80, false positive rate under 0.05, extraction F1 at least 0.70). Any miss blocked the PR automatically, and if the results file was missing the gate failed to close. Ground truth came from production itself, the replies humans actually sent, not from invented test cases.

(b) Worst failure. A memory update loop went runaway. One shipment record got regenerated 91 times in 24 hours, and the system was queuing 1,700 regeneration tasks an hour. Nothing was wrong in any single run, so no error fired, we caught it through cost monitoring when one week's spend was 92 percent multi save churn. What I owned: I had built triggers on events with no counters or budgets around them. Permanent fix: memory updates now fire on counters with debounce, every record drains through a per record queue, and hard budgets live in code outside the model. And the rule I carry since: instrument cost and volume like you instrument correctness, because the worst failures do not throw errors.

Q03

Your machine

Everything runs on a VM that never sleeps multiple Claude Code sessions live 24×7 with remote control, so my phone is a full terminal into them. Claude is wired into Granola (client meeting notes), Slack, and our AWS/Azure infra, and writes everything it learns into mindmap, a shared knowledge repo which is also how my Claude coordinates with my teammates Claude's when we split a feature.

Two loops run on top: devils-advocate when Claude finishes work, it spawns a Codex agent to review it, and they argue in rounds until the diff survives; and a feedback loop that watches production, root-causes defects, and opens draft PRs on its own. It never merges — humans keep the judgment.

For example sweep surfaced 5 findings and opened a draft PR for Customer Draft before I woke up a session prepped my client call from Granola. It got one thing wrong, a false-positive hallucination the customer had actually stated and one fix patched the symptom, not the cause. I still reviewed every PR, made the commercial call, and talked to the client myself.

Part 2

How you think

Q07

The AI Brain for law firms

I have already built this system once, for freight forwarders instead of law firms. A pricing desk and a law firm have the same shape the real knowledge lives in emails and attachments, the work is a stream of matters (for me, shipments), and the users only trust what they can verify. So I would build the law firm brain exactly the way I built the RFQ agent.

Layers, mapped from what I ran in production. Ingestion connect Outlook and the document system, parse every attachment, extract typed facts where every single claim carries a citation to where it came from, in my system that was a field citations record pointing at subject, body or attachment, here it points at the page of the contract. Memory one living, cited summary per matter, the same thing as my shipment memory (Trace), which rebuilds one clean narrative per shipment from mail scattered across mailboxes, built deterministically first with the LLM only judging gray zones. Storage one isolated database per client, so ethical walls are structural, in freight that was one database per tenant. Agents narrow ones, an intake classifier, precedent search over the firm's own past matters, a drafting agent that only asks a question when a required field is genuinely missing, and a deadline watcher that is plain code with no LLM, because dates that are already extracted do not need a model. Human touchpoints: nothing ever sends itself, every output lands as a draft card the lawyer approves or edits, and every edit is logged, that edit stream was my eval ground truth and roadmap in production and it would be here too.

V1 is one workflow, not a platform: ingest, ask this matter with citations, and deadline alerts for 5 pilot lawyers. Day 30 live, day 60 measuring edit rate, day 90 add the one highest volume routine draft type behind an eval gate. Deliberately out of v1:case law research (Westlaw exists and public law is where hallucinations live), auto sending (trust), a general chatbot (unscoped questions are unverifiable), fine tuning (retrieval plus citations wins at this data size).

Q08

The dice roll

  1. The offer: your marina's phone, whiteboard and paperwork, run by AI, so a call at 7pm in April still becomes a booked haul out.
  2. Agent one, front desk: answers every call and email, quotes slip rates, runs the waiting list, and books lifts, launches and repairs straight into the yard calendar instead of onto a sticky note.
  3. Agent two, yard scheduler: plans each day around the travel lift and the weather forecast, and when a storm moves in it reshuffles the week and texts every affected owner before they can call angry.
  4. Agent three, paperwork and parts: collects insurance certificates before winter storage contracts, orders parts the day a repair is approved, and flags when a 3 week part will break a promised launch date.
  5. Why they pay: one missed call in season is a lost 3,000 dollar haul out, and the office runs on one overwhelmed seasonal person, so 700 dollars a month per yard is cheaper than any hire they can actually find.
  6. First five customers: go in the off season when phones are quiet, run one local yard free through spring launch, then let the owner tell the five yards next door, because marina operators all know each other.
  7. After 50 customers the system knows how long every job actually takes per boat type, real parts lead times by supplier, which weather forecasts actually cancel work, and regional slip pricing, none of which a new competitor can scrape.
  8. It also holds each boat's full service history, and that history follows the boat, so owners start asking their next yard to use it.
  9. What kills it: owners who insist on talking to Dave, the guy they have known for 20 years, and yards that quietly keep the whiteboard.
  10. I would know in 90 days from three numbers: what share of calls the agent handles without a human, what share of bookings it creates, and whether staff still update the whiteboard by hand, if the whiteboard survives spring launch, the product failed.
Q10

Everyone improved, everything got worse

Every team hit its own number by quietly passing cost downstream. Sales closed faster by promising more, Scoping went faster by writing thinner docs, Build shipped more by cutting tickets smaller and deferring debt, CS responded fast but shallow. All dashboards are correct because the damage lives between the teams, in the handoffs and queues, and end to end delivery time belongs to nobody.

Look first at the handoffs: map the last ten projects into time being worked vs time sitting in a queue between teams. Most of the delay will be waiting, and most quality complaints will trace back to thin scoping.

One change: one shared number above all four dashboards, signed to delivered with a quality gate, reviewed weekly by all four leads together. I built this exact thing for AI pipelines, one board across the whole system where every issue becomes a Linear ticket with a named owner and a Slack alert, because green team dashboards mean nothing when the system number is falling.

Q12

The hardest calls

(a) Hardest call. At Sidecar I scrapped my own design for the shipment memory system after weeks of work, it was hitting 17 percent recall at 2 to 4 dollars per record. Admitting my approach was wrong in front of the team and rebuilding it deterministic was the hard part. The rebuild got 100 percent recall at 11 cents.

(b) Delivery failure. We found 21 percent of customer requests were being silently dropped, the system decided to reply and then nothing went out, no crash, no alert. My fault: I had built alerts for errors but nothing that measured absence. Permanent fix: a daily check that looks for missing replies, and my rule since then, alert on silence, not just errors. It is now under 1.5 percent a day.

Q13

Hire or fire

(a) My rule: if the output is checkable, build the system, if it needs judgment or a relationship, hire the person. Right call replaced a daily standup call and client report with one pipeline, a week to build, ran untouched for months. Wrong call: tried to automate eval labeling with LLM judges, an audit corrected 159 of 490 labels, had to bring human experts back.

(b) Restructure first: move them off the client critical path, cut work into 2 to 3 day demoable chunks, and I own the client deadline with buffer. My line: I can absorb missed deadlines, I cannot absorb surprises. The third time a slip arrives unannounced, or the client hears about a problem before I do, we part ways and I say exactly why.

Q14

Your first 30 days

Week 1: ship a real PR through their review myself, sit with each dev to see where time actually goes, then pair with the most open one and finish their days long ticket in hours, in front of them. Week 2: build the shared setup, repo context files, an AI review agent on every PR, one automation for the biggest time sink, all opt in. Week 3: every dev runs one of their own tickets through it with me, their complaints tune it, skeptics convert on their own work not demos. Day 30: numbers not claims, cycle time and review turnaround before vs after plus one two week feature shipped in three days, and if the numbers are not there I say so, 5x is what I believe, not what I promise. I will make claude skills for each repo and task so that we can ship things faster at 10x.
